# Поиск и доступность для ИИ-агентов

Публичный HTML сайта Sotto — основной источник информации для поисковых систем и ассистентов. Важные сведения о продукте, выборе моделей, установке и ответы на частые вопросы должны быть доступны без выполнения JavaScript. Поддерживайте точность английской и русской версий и возможность ссылаться на них, используя один канонический URL для каждого языка.

[Рекомендации Google по поиску с ИИ](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) распространяют обычные принципы поисковой оптимизации на генеративные ответы. Ни специальная разметка для ИИ, ни `llms.txt` сами по себе не повышают позиции в Google. Текстовые сводки на сайте — дополнительное удобство для агентов, которые ими пользуются, а не условие индексации или гарантия цитирования.

## Содержание и метаданные

Используйте заголовки и описания, которые обозначают решаемую задачу и поддерживаемые системы. Видимый вводный текст на первом экране объясняет категорию продукта, а основной заголовок может сохранять фирменный стиль. Точно описывайте локальное распознавание, необязательные облачные сервисы, стоимость, требования к процессору и поддерживаемые платформы. Не создавайте впечатление, что каждая модель поддерживает все языки или выводит текст в реальном времени.

Сверяйте сведения о продукте с манифестом нативного приложения и публичными руководствами. Редактируйте локализованные ответы FAQ в одном месте: видимый ответ, его структурированные данные и соответствующая текстовая сводка используют общий словарь. При изменении формулировок сохраняйте идентификаторы вопросов, чтобы цитаты и опубликованные ссылки продолжали работать.

Узел `WebSite` сообщает поисковым системам [название сайта](https://developers.google.com/search/docs/appearance/site-names). Обе языковые версии описывают одно приложение, а страницы и FAQ имеют отдельные URL для каждого языка. `SoftwareApplication` описывает приложение, однако для [расширенного результата Google о программе](https://developers.google.com/search/docs/appearance/structured-data/software-app) также нужна настоящая оценка или рецензия. Не выдумывайте их и не используйте звёзды GitHub как пользовательские оценки.

Структурированные данные FAQ сохраняются как машиночитаемое описание видимых ответов. Google [убрал расширенные результаты FAQ в мае 2026 года](https://developers.google.com/search/updates#may-2026), поэтому не представляйте эту разметку как способ получить расширенное отображение в поисковой выдаче.

## Хостинг и доступ поисковых роботов

В репозитории доступ роботам разрешён через `robots.txt`, а карта сайта доступна публично. Cloudflare может добавлять собственные управляемые директивы в начало файла или применять отдельные правила WAF, поэтому после каждого изменения хостинга проверяйте ответ опубликованного сайта. Локальный предпросмотр не воспроизводит эти механизмы. См. документацию по [управляемому robots.txt](https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/) и [управлению ИИ-роботами](https://developers.cloudflare.com/ai-crawl-control/features/manage-ai-crawlers/).

Разделяйте доступ для поиска и выполнения запросов пользователя агентами и доступ для обучения моделей. OpenAI описывает [OAI-SearchBot для поиска в ChatGPT](https://developers.openai.com/api/docs/bots); его политика независима от политики GPTBot, используемого для обучения. При диагностике блокировок проверяйте подтверждённую принадлежность робота провайдеру или опубликованные диапазоны IP-адресов. Успешный запрос с подставленной строкой user-agent сам по себе не доказывает, что настоящий робот имеет доступ к сайту.

После публикации проверьте следующие ответы сайта:

| Запрос | Ожидаемый результат |
| --- | --- |
| HTTP-версия страницы или версия с `www` | Постоянное перенаправление на HTTPS на `sotto.today` с сохранением пути |
| `/`, `/ru/`, обе страницы политики конфиденциальности | 200, читаемый HTML, canonical на собственный URL, взаимные ссылки hreflang |
| `/robots.txt`, `/sitemap-index.xml`, `/sitemap-0.xml` | 200, корректный текст/XML, без страницы проверки посетителя |
| `/llms.txt`, `/ru/llms.txt` | 200, обычный текст в UTF-8 с актуальными сведениями о продукте |
| Несуществующий путь в корне сайта или в русской версии | Настоящий ответ 404 на соответствующем языке, noindex |
| Изображения для социальных сетей, стили, скрипты и шрифты | Доступны без cookies и авторизации |

Проверяйте доступ настоящих роботов через инструменты проверки URL в панелях вебмастеров и журналы запросов Cloudflare. Сохраняйте защиту WAF: исправляйте конкретное правило, блокирующее нужный поисковый или агентский трафик, вместо глобального отключения защиты.

## Настройка панелей вебмастеров

Эти действия требуют доступа к учётным записям владельца домена и выполняются отдельно от публикации кода.

1. Подтвердите права на `sotto.today` в [Google Search Console](https://search.google.com/search-console), [Bing Webmaster Tools](https://www.bing.com/webmasters/) и [Яндекс Вебмастере](https://yandex.com/support/webmaster/en/service/quick-start.html). Подтверждение через DNS позволяет не добавлять на лендинг скрипты отслеживания.
2. Отправьте `https://sotto.today/sitemap-index.xml`. Проверьте обе главные страницы: выбранный канонический URL, отрисованное содержимое и возможность индексации. После существенных изменений запросите повторный обход; отправка запроса не гарантирует индексацию.
3. Рассмотрите [Cloudflare Crawler Hints](https://developers.cloudflare.com/cache/advanced-configuration/crawler-hints/) для уведомлений IndexNow при обнаружении изменений по сигналам кеша. Через панели вебмастеров убедитесь, что механизм работает при текущем способе публикации статических файлов. Если нужны явные уведомления, следуйте [протоколу подтверждения прав и отправки URL IndexNow](https://www.indexnow.org/documentation). Используйте один механизм отправки и запускайте его после успешной публикации.
4. Проверьте разметку опубликованного сайта через [Schema Markup Validator](https://validator.schema.org/) и [Rich Results Test от Google](https://search.google.com/test/rich-results). Синтаксическая корректность описания и соответствие требованиям конкретного элемента поисковой выдачи — разные проверки.

## Измерение результатов и продвижение

Отслеживайте проиндексированные канонические страницы, небрендовые запросы, показы, клики и долю кликов отдельно для каждого языка. Обращайте внимание на подходящие запросы, например «offline voice typing Windows», «local dictation macOS», «голосовой ввод без интернета» и «расшифровка аудио локально». Это гипотезы для контента, а не подтверждённый поисковый спрос; определяйте приоритеты по реальным отчётам о запросах.

Проверяйте опубликованные главные страницы в [PageSpeed Insights](https://pagespeed.web.dev/) для мобильных устройств и компьютеров. При достаточном трафике анализируйте LCP, INP и CLS по данным реальных пользователей. Успешная локальная сборка или одна лабораторная оценка не подтверждают производительность у реальных посетителей. Сохраняйте статический рендеринг, шрифты на собственном сервере, адаптивные изображения и отложенную загрузку. Не добавляйте тяжёлые маркетинговые скрипты без необходимости, подтверждённой измерениями.

Для расширения охвата в первую очередь создавайте полезные материалы о реальном продукте: руководство по установке на Windows с пояснениями о неподписанном установщике, руководство для macOS с настройкой доступа к микрофону и разрешений Accessibility, руководство по выбору модели и пошаговую инструкцию по расшифровке аудиофайлов без интернета. Каждая страница должна решать отдельную задачу с воспроизводимыми шагами и актуальными скриншотами. Переводите материалы и добавляйте ссылки на них из продукта; не создавайте почти одинаковые страницы под варианты ключевых слов.

Публикуйте проверяемые примеры и замеры производительности с указанием модели, оборудования, языка и методики измерения. Явно указывайте ограничения. Поддерживайте единообразные ссылки из репозитория GitHub и примечаний к выпускам на канонический сайт. Добивайтесь независимых обзоров в профильных изданиях и демонстраций от сообщества вместо покупки ссылок или выдумывания отзывов.

Измеряйте переходы из ассистентов там, где их действительно можно наблюдать, и периодически проверяйте типичные вопросы в поисковых ассистентах, записывая дату и URL цитируемых источников. Переходы и цитирование — разные показатели; ни разрешённый доступ робота, ни скачивание текстовой сводки не доказывают, что ассистент рекомендует продукт. Перед включением новой аналитики проверяйте её соответствие политике конфиденциальности сайта.

## Перед слиянием изменений

В каталоге `site/` используйте версию Node из `.node-version` и версию pnpm из `package.json`:

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm build
pnpm test
```

Тесты сравнивают каталог с манифестом загрузок нативного приложения и проверяют сгенерированные HTML и текст. Дополнительно проверьте в браузере прямые ссылки на вопросы FAQ, фильтры моделей и мобильную вёрстку. Проверки после публикации, перечисленные выше, остаются обязательными: сборка не может проверить DNS, правила CDN, права доступа к панелям вебмастеров или индексацию.
